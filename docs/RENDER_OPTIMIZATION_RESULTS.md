# 渲染优化与基线压测

本轮收益集中在多激光和透明交错：窗口 P95 分别下降约 44% 和 7%，十分钟近似同帧率激光负载的应用 CPU 占用下降约 35%。8192 弹与掉落场景的窗口 P95 点估计分别上升 13% 和 21%，峰值内存基本不变。该分支提供可复核的局部优化与实验结果，不代表所有场景全面提速。

后续魔理沙自机激光的裁剪优化与专用压测见 [魔理沙激光渲染](MARISA_LASER_RENDERING.md)，不计入本文历史矩阵。

## 改动范围

分支为 `heny/render-performance`，未优化生产代码基线为 `9aa73c0`。基线与优化版使用同一份 `tools/render_benchmark.cpp`；基线程序在生产渲染代码改动前编译并冻结，二进制签名及工具签名记录在压测元数据中。

本次保持 OpenGL 后端和原有画质，未降低 MSAA、光晕、分辨率、弹量或战斗模拟频率。

- 普通弹透明批次先按原有排序收集、打包，再统一上传；各批次仍保留独立的类型顺序与透明状态，不能跨演员、道具或激光重排。
- 敌激光每帧一次准备和上传，透明切分通过输入索引引用已上传实例；切分范围、整束 UV、端帽和三个绘制 pass 保持原样。
- Collection/Laser 的 uniform 位置在构造时缓存；自机弹与 Bomb 的 uniform 由素材所有者缓存，并随 shader 释放，避免 program ID 复用后留下旧位置。
- 普通弹与激光的实例容量均与 16384 弹池对齐，修复原有 8192 上限。
- 实例上传采用阶段内追加、统一更新并复用固定存储，由驱动同步在途访问；相机矩阵和视锥平面按阶段复用。

## 测量方法

在本机 Apple M5、原生 arm64 Release（`-O3 -DNDEBUG`）上测量。窗口逻辑尺寸 1100×760，实际 framebuffer 2200×1520，4× MSAA，VSync 关闭。未使用无 MSAA 的离屏截图路径作为性能基线。

正式矩阵每场景预热 5 秒、采样 30 秒、重复三次；顺序为 AB/BA/AB，两个图形负载不并行。额外对基线和优化版各以 60 FPS 运行 600 秒激光持续负载，比较相同出帧目标下的资源占用。开始时与 CTest 重叠的短段已作废，不用于正式汇总。

测试为确定性的固定渲染快照。`game` 包含完整 `Game::Draw` 的背景、战场、HUD 与叠加层；它不代表动态战斗模拟或完整遭遇的性能。实际战斗逻辑的正确性另由核心与生命周期测试验证。

`frame` 为窗口绘制循环耗时，包含提交、呈现和限帧等待，不包含采样查询轮询、截图及统计文件导出；`cpu_draw` 是 CPU 侧绘制调用经过的墙钟时间，可能包含驱动阻塞；`gpu` 是异步 `GL_TIME_ELAPSED` 区间，范围覆盖渲染准备和提交，不是独立片元着色器耗时。CPU/GPU 数据不能相加。

GL 计数通过转发原始函数指针采集，两版使用相同统计开销；上传次数/字节数统计 `glBufferSubData`，包含模型和 rlgl 精灵批次，不包含 `glBufferData` 的存储重命名。CPU 百分比以一个核心为 100%。`/usr/bin/time -l` 补充进程总 CPU 和峰值驻留内存。未采集可靠的功率瓦数，不能把 CPU 占用变化称为实测节电比例。

测量在电池供电下进行，恢复会话开始为 80%，结束为 52%；未锁定 CPU/GPU 频率，系统未记录热警告。这些条件限制跨机器和跨运行环境的外推。

## 复现入口

```bash
cmake -S . -B build-render -DCMAKE_BUILD_TYPE=Release \
  -DFETCHCONTENT_SOURCE_DIR_RAYLIB="$PWD/build/_deps/raylib-src"
cmake --build build-render --target koumakyou render_benchmark -j 6

# 二进制所在目录需有完整 assets；默认游戏构建会完成复制。
./build-render/render_benchmark assets/runtime output/render-performance/manual \
  lasers 5 30 3 4 0

# 已记录实验的程序和素材保留在本机忽略目录，完整素材另有逐文件 SHA-256 清单。
BASELINE_EXE="$PWD/output/render-performance/binaries/baseline/render_benchmark"
BASELINE_ASSETS="$PWD/output/render-performance/binaries/frozen-assets"
python3 tools/compare_render_performance.py \
  --baseline "$BASELINE_EXE" --baseline-assets "$BASELINE_ASSETS" \
  --optimized build-render/render_benchmark --assets assets/runtime \
  --output output/render-performance/reproduction --soak 600 --soak-fps 60

# 暂停恢复时追加 --resume；仅保留已完成整组的场景。
python3 tools/verify_render_images.py output/render-performance/reproduction
```

模型/shader 签名与完整素材快照分别记录，图集和其他素材的完整逐文件 SHA-256 位于 `binaries/frozen-assets-sha256.json`；冻结程序及素材可直接复现，避免依赖临时目录。

正式数据位于忽略目录 `output/render-performance/fixed/`：`results.csv` 为 60 轮汇总，子目录包含逐帧 CSV、截图和运行日志；`metadata.json` 记录二进制及素材签名、环境与暂停恢复会话。

## 正式矩阵结果

下表为三次重复各自 P95 的中位数，单位 ms；变化为优化版相对基线。负数表示窗口绘制循环耗时下降。

| 场景 | 基线窗口 P95 | 优化窗口 P95 | 变化 | CPU 绘制 P95：基线 → 优化 | GPU 区间 P95：基线 → 优化 |
|---|---:|---:|---:|---:|---:|
| empty | 3.548 | 3.624 | +2.1% | 0.062 → 0.070 | 0.000 → 0.000 |
| mixed1024 | 4.656 | 4.416 | -5.1% | 3.242 → 3.162 | 2.293 → 2.236 |
| mixed8192 | 10.651 | 12.035 | +13.0% | 9.134 → 9.499 | 7.734 → 8.305 |
| interleaved | 16.605 | 15.392 | -7.3% | 16.148 → 14.162 | 15.201 → 13.236 |
| lasers | 13.875 | 7.774 | -44.0% | 11.528 → 6.119 | 11.380 → 5.873 |
| shots | 5.308 | 5.207 | -1.9% | 2.900 → 2.904 | 1.478 → 1.325 |
| drops | 5.883 | 7.096 | +20.6% | 2.273 → 2.505 | 0.941 → 0.963 |
| bomb | 5.408 | 3.164 | -41.5% | 0.663 → 0.657 | 0.505 → 0.503 |
| game | 7.347 | 7.188 | -2.2% | 3.574 → 3.390 | 11.011 → 10.863 |
| menu | 7.555 | 7.389 | -2.2% | 3.231 → 3.185 | 1.379 → 1.444 |

场景内容：`mixed1024`/`mixed8192` 为十类混合普通弹；`interleaved` 为 4096 弹、24 个演员、48 个道具和半透明出生；`lasers` 为 1024 弹、32 束激光和 24 个演员；`shots` 为 512 自机弹，`drops` 为 512 道具，`bomb` 为近景巨束；`game` 是开局推进约六秒后的完整绘制快照，`menu` 是标题菜单。

激光场景窗口 P95 下降约 44%，GPU 区间 P95 下降约 48%；透明交错窗口 P95 下降约 7%。8192 普通弹的窗口 P95 点估计上升 13%，目前不能宣称这一路径提速。其三轮差异不一致，原始数据必须随结果一起保留。

Bomb 窗口 P95 虽下降约 42%，CPU/GPU P95 却基本相同，不能把全部变化归因于代码优化。掉落场景窗口 P95 上升约 21%，同样保留为负面结果。

未修改的菜单路径也出现了基线首轮 CPU P95 约 1.58 ms、后续约 3.23～3.27 ms 的漂移，两版截图完全一致。这表明非锁频、真实桌面窗口测量存在环境波动；对较小差异不能仅凭本轮点估计作强因果判断。

确定的结构变化：普通混合弹绘制次数仍为 26；透明交错总上传次数由 201 降为 98；激光场景由 294 降为 99，切分仍为 140 段、总绘制仍为 1380 次。两类场景的逐帧 uniform 名称查询分别由 4631、4632 次降为 0。这里的总上传包含仍未实例化的精灵批次。

暂停前已完整完成的空场景保留；被暂停的 1024 弹半组已归档并整组重测。最终矩阵共 60 个完整运行记录，不跨暂停拼接半组。

## 十分钟持续负载结果

同一激光场景，两版均设置 60 FPS 上限，分别测量 600 秒。实际出帧量接近；CPU 百分比是进程单核等效占用，不包含 WindowServer，也不是整机能耗。

| 指标 | 基线 | 优化 | 变化 |
|---|---:|---:|---:|
| 实际采样 FPS | 58.262 | 58.398 | +0.2% |
| 单核等效 CPU 占用（%） | 51.835 | 33.757 | -34.9% |
| CPU 绘制 P95（ms） | 14.435 | 6.980 | -51.6% |
| GPU 区间 P95（ms） | 14.476 | 11.335 | -21.7% |
| 窗口循环 P95（ms） | 17.791 | 17.220 | -3.2% |
| 进程最大 RSS（MiB） | 549.578 | 551.641 | +0.4% |
| 进程峰值 memory footprint（MiB） | 975.267 | 975.423 | +0.0% |

CPU 单核等效占用由 51.84% 降为 33.76%，下降约 34.9%。两版均保留 140 个激光片段及每帧 1380 次绘制，上传由 294 次降为 99 次。功率瓦数未采集，因此不把它表述为整机节电 35%。

实际循环约 58.3/58.4 FPS，未精确达到设置的 60；等待与呈现开销计入循环。CSV 的 `over_60` 是严格超过 16.67 ms 的样本比例，不能当作屏幕实际掉帧率。

内存峰值没有降低：Darwin `time -l` 的最大 RSS 与 peak memory footprint 均覆盖启动、加载和截图导出，不是纯绘制瞬间。附加 ps 样本仅成功覆盖优化版后段，不用于 A/B 稳态内存结论。

## 验证记录

新增回归比较立即上传与帧内多批上传的 GPU 像素，覆盖空批次、混合弹种、半透明主体、激光 variant 重排、裁切区间、上传前句柄误用、16384 实例及 shader 缓存重新加载。

Release 构建通过，最终 CTest 为 7/7 通过（217.98 秒）。图形模型运行时、透明遮挡和完整资源生命周期测试通过；一面在 300.983 秒结束，30/60/120/144/240 FPS 的轨迹对照一致。

16384 弹边界另做两秒短测：基线抛出 `Shared projectile capacity exceeded`，优化版完成 121 帧，窗口 P95 约 22.4 ms。它用于容量验证，不能视为稳定达到 60 FPS；失败基线不计算速度比。原始结果在 `boundary/`。

`verify_render_images.py` 检查了 30 组实际窗口截图：除 `game` 右下角实时 FPS 文字的明确区域外，所有像素一致。完整结果在 `image-verification.json`，构建、CTest 与图形回归日志在 `validation/`。

## 成本与边界

批次描述、每帧激光映射和更大的实例缓冲增加了内存成本。普通弹 GPU 实例存储由 0.75 MiB 增为 3 MiB，激光由 0.5 MiB 增为 1 MiB，合计逻辑分配增加 2.75 MiB；CPU 打包缓存也随容量增大。它们不等于完整 GPU 驻留量，需与进程 RSS 和减少的驱动等待一起评估。主体与装饰仍分别准备；自机弹、道具仍逐对象绘制。本文所测版本的激光在片元阶段裁切整束；后续魔理沙激光已另行提前裁剪，敌激光仍保留原路径。

透明顺序与绘制调用数原则上不变；本次主要减少上传调用、重复参数解析和 uniform 名称查询。GPU 负载主导的场景可能收益有限，完整 HUD 场景也可能被不受本次修改影响的 UI 和呈现成本限制。正式结果必须同时列出退化场景。

## 已淘汰的候选方案

最初同时尝试了缓冲存储重命名。在独立完成回归之后的 1024 混合弹单轮 30 秒采样中，窗口平均耗时仅从 4.123 ms 变为 4.039 ms，GPU 计时区间均值却从 2.349 ms 拉长到 26.351 ms。它可能涉及排队或驱动调度变化，未通过 GPU trace 确认具体机制；不能把 CPU 调用耗时下降直接当成 GPU 压力下降。因此最终实现撤销反复重命名，保留固定存储和统一上传。该候选数据位于 `validated/`，明确标记为探索结果，不计入最终版的改善比例。

## 后续优先项

优先定位 8192 普通弹和掉落的尾部时延，使用 GPU trace 与更严格的桌面/频率条件区分驱动、呈现和真实渲染成本；再评估实例缓冲按高水位分配以减少容量扩张的内存成本。当前结果不足以支持无条件合并为“全场景降压”版本。Metal 迁移仍需独立原型与相同场景对照，不从本轮 OpenGL 数据推导收益。
