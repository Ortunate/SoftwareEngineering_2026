# 软件工程课程汇报 PPT 脚本

本文提供 koumakyou 项目期末汇报的逐页内容、讲稿和演示安排，按 10 页、8 分钟组织。配套素材见[素材清单](COURSE_PRESENTATION_ASSETS.md)。本文是制作与排练脚本，不是已完成的 PPT。

## 使用方式

- 主线：把二维弹幕玩法改造为第一人称三维游戏，并通过软件工程方法完成设计、实现与验证。
- 页面只放“上屏内容”，完整“口播稿”放入演讲者备注。
- 项目源码与开发记录沿用现有 GitHub 仓库；第 9 页展示 Wiki 发布页，第 10 页展示发布包，具体链接按实际发布位置填写。
- 所有 `【待填写：……】` 均须按真实情况替换；未完成事项不得在讲稿中表述为已经完成。
- 功能范围以最终演示版本为准。README、设计文档与代码存在历史描述差异时，先统一提交版本的口径。
- 不要求每位成员在台上发言；具体安排依据课程要求和排练结果确定。成员贡献必须在第 3 页和项目报告中可追溯。

## 第 4 页：原型覆盖完整核心流程

**页面标题**：从配置选择到战斗结算，形成完整交互流程

**本页结论**：关键入口、返回和结果反馈都有明确去向。

**上屏内容**：

> 首页 → 难度／角色／机体／模式配置 → 战斗 → 结果处理 → 返回或再次挑战

- 练习：进入目标内容，缩短重复前置流程
- 设置：调整键位、音量和鼠标灵敏度
- 结果：按实际入口提供成绩或录像相关操作

**画面构建**：展示四至五张等比例截图，用箭头连接。原型和实机分别标注；用一个局部对比说明实际发生过的交互调整。

**口播稿**：

> 我们把交互围绕一条完整流程组织：玩家从首页进入配置，确认后开始战斗，再通过结果页面返回或继续挑战。练习入口帮助玩家直接进入需要训练的内容，设置入口则满足不同操作习惯。原型展示页面之间的跳转关系，实际实现还要处理取消、返回、暂停和保存失败等分支，保证流程能够完整结束。

**使用要求**：使用原型截图与流程说明展示页面跳转关系；从实机补做的交互说明应明确其制作时间，不能冒充早期原型。

**素材**：S03～S07 页面截图；D04 原型流程说明。

## 第 5 页：统一框架组织关卡与战斗

**页面标题**：通用系统与关卡内容分离，支持持续扩展

**本页结论**：关卡配置负责内容，通用模块负责调度与执行。

**上屏内容**：

- 应用层：输入、状态切换和生命周期
- 内容与行为：事件表、普通演员、Boss、对话
- 战斗系统：弹幕、碰撞、掉落和结算
- 表现与资源：渲染、HUD、音频、素材加载及释放
- 本地数据：设置、成绩、录像

**画面构建**：将上述模块画成可编辑架构图；用一条醒目箭头突出以下调用链。该图是汇报用职责概览，不表示所有模块已经使用独立控制器或只读快照实现。

> StageDirector → StageContent::HandleEvent → StageEventSink（Game）→ ActorPool／Boss／对话

**口播稿**：

> 系统设计的重点，是把通用能力与具体关卡内容分开。应用层负责输入、状态和生命周期；关卡时间轴描述何时发生事件，内容层提供演员、Boss、对话和资源配置。StageDirector 触发事件后，由 StageContent 分发到 Game，再交给演员池或其他执行对象。移动、发射和弹幕管理由通用组件承担，渲染与音频负责呈现。这样增加关卡时，可以沿用同一条执行链，并针对各关内容分别验证。

**素材**：G03 架构图；D05、D06 设计文档；相关接口定义。

## 第 6 页：空间适配与时序一致性

**页面标题**：空间规则与逻辑时钟共同决定游戏体验

**本页结论**：三维适配需要同时处理空间判定和时间语义。

**上屏内容**：

| 难点 | 设计 | 验证方式 |
| --- | --- | --- |
| 第一人称下的空间弹幕 | 世界坐标、三轴移动，球形／胶囊等碰撞几何 | 空间示意、实机画面与判定用例 |
| 不同帧率下保持节奏 | 60 Hz 内容帧；演员行为默认 120 Hz 补算；显示帧率独立 | 多显示帧率对照、参考差分与事件边界测试 |

**画面构建**：左侧用“玩家判定点＋弹体／光束”说明空间关系；右侧用时间示意图表示一个 60 Hz 内容帧对应两个 120 Hz 行为步。注明这不是“所有子系统都使用同一种更新方式”。

**口播稿**：

> 我们重点解决了空间和时间两个问题。空间上，第一人称视点对应玩家判定位置，弹体和光束采用明确的三维碰撞几何，帮助玩家理解移动与受击的关系。时间上，关卡与行为的内容帧按 60 Hz 解释，演员默认以 120 Hz 补算，因此每一步推进半个内容帧。显示更新不能直接作为逻辑计数。我们通过不同显示帧率、事件边界和独立参考对照，检查移动与攻击节奏是否保持一致。

**素材**：G04 空间判定图；G05 时间示意图；D07 关卡方法；D08 测试证据。

## 第 7 页：实机演示

**页面标题**：从配置到空间战斗，验证核心体验

**本页结论**：用一条短演示证明可操作的产品能力。

**上屏内容**：以视频或实际游戏画面为主，角落仅保留三条提示：三维移动、代表性弹幕、完整结果反馈。

### 演示分镜与同步讲稿

| 相对时间 | 画面与操作 | 同步口播 |
| --- | --- | --- |
| 0～15 秒 | 从首页进入配置或练习入口 | “首先展示配置与练习入口，玩家可以选择对应的角色和挑战内容。” |
| 15～35 秒 | 进入预先确定的场景，平移、升降、适度转向并射击 | “战斗中，观察方向、移动和高度共同影响空间判断。这里可以看到三轴移动与瞄准操作。” |
| 35～65 秒 | 展示一组代表性空间弹幕，保持可读视角 | “这组攻击保留了旋转／包围等主题，同时加入纵深和高度变化。玩家需要结合距离与方向选择路线。” |
| 65～80 秒 | 展示一次 Bomb 和暂停／继续 | “Bomb 提供应对危险的手段，暂停后可以看到战斗时序被冻结，继续后从原状态恢复。” |
| 80～100 秒 | 切换到预录好的结果或录像片段 | “结果流程支持对应的成绩或录像操作。录像还能用于重新观察同一段战斗。” |
| 100～110 秒 | 返回 PPT，进入测试页 | “下面介绍我们怎样验证这些功能和运行表现。” |

### 演示准备

- 主片控制在约 100 秒，另外预留约 10 秒返回 PPT；保留一个 60 秒压缩版用于超时情况。
- 可以拼接不同阶段的真实操作，但在剪辑处标注“片段切换”，不伪装成一次连续通关。
- 结果页面难以在短时间自然到达时，直接使用提前录好的片段，不在现场临时等待。
- 录屏优先使用 1920×1080、16∶9、60 FPS；设备不足时使用稳定 30 FPS。MP4 / H.264 为建议交付格式，不把格式建议当作性能指标。
- 游戏声音低于讲解声音；避免鼠标快速甩动和过密剪辑，保证投影时可以看清。
- 使用最终演示构建与匹配的录像；不要临时修改录像格式或内容版本。
- 准备离线 MP4、实际运行包和演示专用配置，网页不作为现场演示的唯一依赖。
- 如果使用调试能力或特殊预设，应标明；它们的记录不能作为正式通关成绩或正常测试结果。
